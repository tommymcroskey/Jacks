## Correctness and evidence findings

1. **P1 — unchecked net-deposit addition.** `src/deposit.cpp:39` adds amount to
   net deposits without checking representability. The check at lines 30-33 only
   protects cash. A structurally valid state with cash 0, quantity 0, absent mark,
   net deposits INT64_MAX, sequence 0 and deposit amount 1/sequence 1 must return
   overflow. In the independently compiled MSVC Debug probe, it instead returned
   DepositApplied with cash 1 and net deposits -9223372036854775808. This is signed
   overflow/undefined behavior; the observed wraparound is not a portable promise.
   Historical reachability is not a validity requirement of this accepted API.
   The contract explicitly validates supplied structure, not flow provenance.
   Add a failing counter-boundary test before correcting this arithmetic.

2. **P2 — skipped cases do not validate their expected outcomes.**
   `tests/deposit_test.cpp:77,92,107,122,137,152,167,182,197,216,230,244,258,263`
   contain GTEST_SKIP rather than assertions. Of 19 deposit cases, only five
   currently check outcomes. The others will accept any normally returned result
   as a skip. In the test-first parent, most call the throwing stub before the skip;
   a red result there can disappear simply because the function stops throwing,
   without the intended error being checked. Parent source inspected, not rerun.
   Replace meaningful placeholders with assertions; remove/document an impossible
   case rather than retaining a permanently skipped test as evidence.

3. **P2 — sequence/overflow fixture does not contain overflow.**
   `tests/deposit_test.cpp:266-279` uses INT_MAX with cash 12 and net deposits 18.
   Both sums fit signed 64-bit on our toolchain. The test checks invalid sequence,
   but cannot protect the claimed precedence over overflow. Choose values that
   independently violate both intended rules. This repeats the previously discussed
   distinction between int and int64 limits; audit each fixture against its name.

4. **P2 — success and rejection state guarantees lack evidence.**
   The successful case at lines 283-296 checks only cash and equity. It omits
   updated net deposits/sequence and preserved quantity/mark. No test asserts
   unchanged input fields or corrected same-sequence retry after a rejection.
   Cash-only absent-mark success and exact-limit success also remain required by
   the assignment. Add focused checks, not an exhaustive input Cartesian product.

## Interface, maintainability and preference

- **Interface:** lines 49-50 map every candidate valuation error to overflow.
  The written contract maps unexpected missing/invalid input to invalid_state.
  Those errors are unreachable with the current validated state and unchanged
  holdings/mark, so this is contract alignment rather than a reproduced additional
  runtime defect. Preserve the documented mapping explicitly before acceptance.
- **Maintainability:** the first test constructs named current/deposit objects
  but ignores them at line 28 and repeats literals. Use the named fixture so
  edits change what is actually exercised, not an unused description.
- **Maintainability:** source lines 24-25 say last_sequence is "clamped"; it is
  validated, not modified. The useful observation is that last_sequence >= 0
  makes a strictly greater sequence positive. Make the comment describe that.
- **Consistency:** use snake_case for newState and make it const when it is never
  modified, consistent with surrounding variables. Do not add abstraction to fix
  these local issues. Five trailing-whitespace locations fail diff-check.
- **Preference:** smaller unrelated fixture values can reduce arithmetic noise;
  unusual boundary values are justified where they exercise the specific rule.
  Explicit labeled aggregates and a fatal variant check remain good choices.
