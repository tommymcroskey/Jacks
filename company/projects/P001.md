# P001: explain changes in portfolio value

## Proposed purpose

Build and independently verify a small accounting system that explains how a portfolio changes value. It will become a foundation for later backtesting. This is an accounting project, not evidence of alpha.

## Initial scope

- Tiny, deterministic synthetic examples that can be checked by hand.
- One currency, cash, and at most one long asset position; no borrowing, shorts, or derivatives.
- Explicit prices, executed trades, fees, and external cash flows.
- Define event order, units, precision, and what data each calculation may observe.
- Decide whether splits/dividends belong in a follow-up after the basic ledger is accepted.

Do not choose an entire production architecture or implement the backtester during kickoff. Prefer a small C++ contribution if suitable; engineering must first assess the local toolchain and discuss the apprentice's experience. No installation is needed to write the kickoff proposal.

## Kickoff deliverables

Each specialist produces one concise brief (target at most 800 words, excluding a small table/example) on its branch. Each is a proposal, not a decision. Explain vocabulary and reasons. Identify one useful independent next task and one possible apprentice contribution. End with a handoff and stop.

### ENG-001

Read the engineer role. Inspect available compiler/build tools read-only. Propose the smallest component boundary, how to build/test it, and which company conventions must exist before implementation. Do not install tools, implement the component, or assign L-001 yet. Include a short conversation prompt to understand the apprentice's current approach without an interview-style exam.

### RES-001

Read the researcher role. Explain the economic/accounting question, the distinction between profit and deposited money, and what measurements a future researcher would need. Propose a tiny example and acceptance questions. Do not assert measured results or implement the apprentice contribution.

### RISK-001

Read the risk role. Propose falsification checks for the ledger: reconciled cash/positions/equity, fees, external flows, invalid events, and event timing. State independent expected-value checks and the conditions required to trust the first component. Keep this proportional to the scope.

## Proposed project acceptance criteria

1. Explicit accounting/event contract with units and assumptions.
2. Hand-verifiable expected outcomes independent of implementation.
3. Minimal implementation with meaningful reconciliation and edge-case checks.
4. Reproduction instructions verified by someone other than the author.
5. Review records citing exact artifacts and versions.
6. Apprentice explains their contribution and its limits; accepted work is actually used.

The kickoff review can revise these criteria with reasons before implementation begins.
