## Why this is next

Your valuation, deposit, profit and mark functions form our accounting foundation.
The next milestone is a small synthetic trading lifecycle: observe a price,
make a decision, supply a later execution and fee, and reconcile the account.
Seniors own that surrounding scenario and chronology. Your part is `apply_fill`
in `include/jacks/fill.hpp`: record one supplied buy or sell completely, or return
an error. A **fill** is an asserted execution with a quantity and execution price;
this function does not decide whether the market would have executed an order.

Execution price and valuation mark are separate inputs with separate meanings.
Keep the current mark unchanged, even when it differs from execution price.
Use `apply_mark` beforehand if the account needs a valuation mark. This milestone
has no historical performance claim. Historical data needs a separately reviewed
source, timing and price-meaning policy before use.

## Contract: apply these stages in order

All amounts use signed 64-bit integers, money in minor CU and whole asset units.
Reuse `DepositState` as the existing account snapshot; no carrier rename is needed.
Let **gross** mean the mathematical fill quantity times execution price.

1. Validate the current state as in L-004: cash, quantity, any present mark,
   net deposits and last sequence are nonnegative, and `calculate_equity` succeeds.
   Otherwise return `invalid_state`. Nonzero counters are allowed. An absent mark
   with zero holdings is structurally valid; an absent mark with holdings is not.
2. Return `invalid_fill` for a side other than `buy` or `sell`, quantity <= 0,
   execution price <= 0, or fee < 0. Zero fees are valid. Zero execution prices
   and free asset transfers are outside this assignment; zero valuation marks
   remain valid. The supplied fee is the total fee for this fill, charged once.
3. Sequence must be positive and greater than the current last sequence;
   otherwise return `invalid_sequence`. Gaps are valid. Deposits, marks and fills
   use the same sequence. Sequence alone proves no market-data timing property.
4. An absent current valuation mark returns `missing_mark` for either side.
   Even a cash-only account must receive a mark before applying a fill.
   Do not use execution price as an implicit mark.
5. A sell exceeding the current quantity returns `insufficient_quantity`.
   Selling the entire holding is valid; borrowing and short positions are excluded.
6. Gross and final quantity must each fit in `int64_t`; otherwise return
   `overflow`. Final quantity is current quantity plus bought units or minus sold
   units. The gross bound is an explicit supported cash-flow limit, even if fees
   could make net proceeds fit.
7. The mathematical final cash is `cash - gross - fee` for a buy and
   `cash + gross - fee` for a sell. If negative, return `insufficient_cash`.
   If final cash exceeds `INT64_MAX`, return `overflow`. A sell fee may use both
   proceeds and existing cash; it need not be <= proceeds.
8. If candidate equity exceeds `INT64_MAX`, return `overflow`.
   Reuse `calculate_equity` for candidate valuation. Its other domain errors
   are unreachable after these checks; no defensive mapping is required.

These are ordered stages, not a single global priority for `overflow`: a gross
or quantity overflow is checked before affordability; cash and equity overflow
come afterward.
Never perform overflowing signed arithmetic, including in validation expressions.
The intermediate sums `cash + gross` and `gross + fee` do not have to fit when the
final result does. For example, a sell from cash `INT64_MAX`, one held unit and
mark zero, with execution price 1 and fee 1, leaves cash `INT64_MAX` and succeeds.

On success return `FillApplied` with checked equity and a new state. Change only
cash, quantity and last sequence; preserve mark and net deposits. Trade proceeds
are not external deposits, and a fee is not an external withdrawal. Existing
`calculate_profit` therefore reflects price changes and fees without new profit
fields or cost-basis accounting. Both inputs stay unchanged on success or error;
an error returns no new account state and consumes no sequence.
