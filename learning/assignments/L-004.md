# L-004: change an asset's mark without moving cash

## What you are building

A **mark** is the supplied price used to value each held asset unit. A new mark
can change equity without a deposit, withdrawal, or trade. The resulting gain or
loss is unrealized: it is a valuation change, not cash received or a promise that
the holding can be sold at that price.

Implement `apply_mark` from `include/jacks/mark.hpp`. It accepts an account
snapshot and one required numeric mark with a sequence, returning a new snapshot
and equity or a tagged `MarkError`. Reuse `calculate_equity` for valuation.

We retain the existing `DepositState` carrier to avoid renaming accepted APIs in
this small increment. Its fields now serve both deposit and mark transitions;
`last_sequence` means the last accepted account event, regardless of those two
types. This is explicit naming debt, not a separate deposit-only state rule.

## Contract, in error-precedence order

1. Current state must be structurally valid: cash, quantity, any present mark,
   net deposits and last sequence are nonnegative, and current valuation succeeds.
   Otherwise return `invalid_state`. Nonzero current counters are allowed, as in
   `apply_deposit`; the replay runner's new-run restriction does not apply here.
   This operation cannot repair an invalid old snapshot. A missing old mark with
   zero holdings is valid; with positive holdings it is invalid.
2. A negative supplied mark returns `invalid_mark`. Zero is valid. The event
   always contains a number; it cannot clear the mark to absent.
3. Sequence must be positive and greater than the current last sequence; otherwise
   return `invalid_sequence`. Gaps are allowed. One sequence orders deposits and
   marks together; it is not a timestamp or evidence of market-data freshness.
4. If candidate equity is unrepresentable, return `overflow` before any unsafe
   arithmetic. Reuse valuation rather than duplicating its checked multiplication.
   After these validations its other domain errors are unreachable; no extra
   defensive branch or unreachable test is an acceptance requirement.

Success changes **only the mark and last sequence**, preserving cash, quantity,
and net deposits, and returns candidate equity. Same-price updates and updates
with zero holdings still succeed and consume their sequence. Caller inputs stay
unchanged on success and failure; rejection returns no new state or consumed
sequence. These aggregates validate structure, not historical provenance.
