## Purpose

The accounting primitives are now available. A backtester also needs to apply
events consistently across a run and explain where a rejected event stopped it.
Implement `replay_account` from `include/jacks/account_replay.hpp`: process a
supplied list containing deposits, mark updates and fills using the accepted
functions. Difficulty comes from composition, typed results and report consistency,
not new financial arithmetic. Keep the existing deposit-only replay unchanged.

An `AccountEvent` is a variant holding exactly one of the three event types.
An accepted step retains the matching `DepositApplied`, `MarkApplied` or
`FillApplied` alternative; a failure retains the original typed error. Thus a
`FillError::overflow` remains distinguishable from a `DepositError::overflow`.

## Contract

1. Validate initialization before processing any event, even for an empty list.
   Opening net deposits and last sequence must both be zero, and the existing
   `calculate_equity` must succeed for the opening snapshot. Otherwise return
   `AccountReplayError::invalid_initial_state`, without an event report. Nonzero
   opening cash or holdings are allowed. Zero holdings with an absent mark are
   valid; a later fill still follows `apply_fill`'s mark requirement.
2. Keep opening state/equity fixed. Visit events in their supplied vector order.
   Call `apply_deposit`, `apply_mark` or `apply_fill` for the corresponding event,
   using the last accepted state. Do not duplicate their validation or arithmetic,
   sort events, renumber sequences, infer prices, or catch and reinterpret unrelated
   allocation failures as domain errors. The existing shared sequence rules apply.
3. On success, append one accepted step with its zero-based input index and the
   exact applied alternative returned by that transition. Its state/equity become
   the report's final state/equity. Preserve every accepted intermediate snapshot.
4. On the first domain rejection, set failure to that index and the exact original
   error alternative/value. Return immediately: no rejected step in `accepted`,
   no change to the last accepted state, and no processing of the remaining suffix.
5. A valid empty run returns an empty accepted trace, no failure, and opening
   state/equity as final state/equity. The same final values apply when the first
   event fails. With all events accepted, failure is absent. Caller inputs remain
   unchanged for every outcome; the report owns its values.

The report describes a COMPLETE history only when failure is absent. Otherwise
it describes an accepted prefix. There is no profit field: a caller can use
`calculate_profit(opening_equity, final_equity, final_state.net_deposits_minor_units)`
because the opening funding counter is zero. That reporting calculation can fail
independently and must not undo accepted events or conceal an incomplete history.

Supplied order is not proof of real-world timing. These are asserted executions,
not orders the runner decides to fill. Data availability, mark interpretation,
decision rules and execution/fee models remain separate future work. No parser,
strategy framework, timestamps, persistence, resume mode or new asset support.
