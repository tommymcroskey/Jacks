# L-007: decode an ITCH Add Order message

Owner: Tommy. Engineering supplies the interface/build setup, Research supplies
literal binary examples, and Risk independently reviews the contract and results.
Begin implementation after the scaffold is reviewed and integrated.

## Purpose

Turn bytes in Nasdaq TotalView-ITCH 5.0 format into a typed C++ value. This is the
first reusable part of a future feed reader and order-book reconstruction system.
It does not reconstruct a book or infer a simulated trade.

Implement `jacks::itch::decode_add_order` in `src/itch_add_order.cpp` and replace
the placeholder in `tests/itch_add_order_test.cpp` with focused tests. Stay on
C++17. There is no new accounting operation or financial overflow calculation.

## Source and input boundary

Authoritative reference: [Nasdaq TotalView-ITCH 5.0 specification](https://nasdaqtrader.com/content/technicalsupport/specifications/dataproducts/NQTVITCHSpecification.pdf),
Data Types (page 4) and Add Order - No MPID Attribution (page 13), inspected
2026-09-29. The layout below freezes this assignment's input contract.

The argument is exactly one **36-byte message payload**, starting with ASCII `A`.
It has no file-length prefix, network packet header, compression, or trailing
message. These bytes may contain zero; this is not a null-terminated string.
The caller is responsible for supplying the payload, independently of how it was
stored or delivered. No downloaded data is needed: use the synthetic wire examples.

Research's [fixture manifest](../../company/briefs/RES-007-itch-fixtures.md) supplies
literal bytes and independently chosen expected fields. The two payloads live in
`tests/fixtures/itch50/add_order_buy.bin` and `add_order_sell.bin`. Tests may embed
the listed literal bytes so they do not depend on a process working directory;
the binary files are also available for inspecting the actual wire representation.

| Field | Byte offset | Byte count | Output |
| --- | ---: | ---: | --- |
| Message type | 0 | 1 | Must be ASCII `A` (0x41) |
| Stock locate | 1 | 2 | `stock_locate`, uint16 |
| Tracking number | 3 | 2 | `tracking_number`, uint16 |
| Timestamp | 5 | 6 | `timestamp_ns`, uint64 |
| Order reference | 11 | 8 | `order_reference`, uint64 |
| Buy/sell indicator | 19 | 1 | `B` (0x42) -> buy; `S` (0x53) -> sell |
| Shares | 20 | 4 | `shares`, uint32 |
| Stock | 24 | 8 | `stock`, all eight bytes in order, including padding |
| Price | 32 | 4 | `price_1e4`, uint32 |

All integer fields are unsigned **big-endian**: the most significant byte appears
first. Do not depend on host byte order, alignment, struct padding, or signed-char
behavior. A six-byte timestamp must not be truncated to a four-byte value.

Price has four implied decimal places: raw 1234567 represents 123.4567. Keep the
integer unchanged. Our accounting uses a different unit scale; no conversion or
rounding belongs here. The timestamp is nanoseconds since midnight, without a
date; it is not a local receive timestamp or proof of when a strategy knew it.

## Contract

1. If the payload length is not exactly 36, return `DecodeError::invalid_size`.
   This includes empty, short, and oversized input.
2. Otherwise, if byte 0 is not `A`, return `DecodeError::unexpected_type`.
   In particular, attributed Add Order `F` is outside this task's supported type.
3. Otherwise, if byte 19 is neither `B` nor `S`, return `DecodeError::invalid_side`.
4. Otherwise return `AddOrder` with every field decoded as above. The output owns
   its fields; it must remain usable after the input vector changes or is destroyed.

This order defines error precedence. Input bytes are never modified, including
on error. A failure contains no partially decoded order. Allocation/resource
exceptions are not additional domain errors to catch and reinterpret.

This is deliberately a lossless wire decoder, not complete semantic validation.
Retain all bit patterns of the numeric fields, including zero and the unsigned
maximum, and all eight stock bytes. Do not add a timestamp/day bound, price bound,
symbol grammar, positive-shares rule, or order-reference lookup. Some decodable
values exceed documented market limits; downstream validation is a separate job.
Successful decoding alone does not make an order valid or a stream book-complete.

## Small test plan

Start with one literal valid message and assert all decoded fields. Get that
test running before implementing the decoder. Then add focused checks for:

- Both side values, padded stock, embedded zero bytes, and multi-byte values that
  expose byte-order or width mistakes. Use Research's literal expected values.
- Raw high-bit/full-width numeric preservation; this is a representation check,
  not a claim that extreme values are economically valid orders.
- Representative empty/short/oversized input and wrong type/side, with the stated
  precedence. A small table/loop is welcome; no test per possible byte length.
- Input immutability and owned output, combined with a successful example.

Use shared fixture/assertion helpers where they remove repetition. No broad
cross-product, separate submission diary, or generalized testing framework.
Run `./tools/l001.ps1 all`. The intentional skip must be gone in your completed PR.

## Scope and start

No file I/O, decompression, network transport, stream framing, message dispatcher,
other message types, order-book mutation, trading strategy, accounting changes,
or performance optimization is required. Do not cast the byte buffer to a C++
struct: the wire layout and the compiler's object layout are different contracts.

Before coding, briefly restate what the 36 input bytes represent, why the price
stays an integer in its own units, and which error wins for a short wrong-type
message. Engineering can help with unfamiliar binary operations without taking
over the implementation. You own your feature branch and PR.
